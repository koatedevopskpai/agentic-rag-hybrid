## What this shows

_Conclusions are written from the measured columns above, not from the hypothesis the benchmark started with._

- **A result `LIMIT` does not bound traversal work.** At every size the capped variant returned 10 rows while `dbHits` was *identical* to the unbounded case (9210 hits at N=2000). The database still expanded the whole neighbourhood; only the number of rows handed back changed. The lower wall-clock is row transfer and rendering, not less work — which is why the conclusion rests on `dbHits` rather than time.
- **A hop bound does bound work.** `max_hops=1` needed 11 dbHits against 9210, because the expansion never leaves the hub.
- **A relationship filter reduces work in proportion to the subgraph it skips.** Filtering to `LINKS` excluded the NOISE branch: 9210 → 8010 hits and 2401 → 2001 rows at N=2000. Useful, but it is not a general work bound — it only helps when the question genuinely excludes an edge type.
- **`dbHits` grows linearly with degree** (≈4.6 hits per reachable node), so expansion cost is proportional to the neighbourhood, not to `top_k`.
- **A true work bound needs degree-aware expansion.** That requires APOC or GDS. Neither is available in the stock `neo4j:latest` image used here (`apoc.version()` and `gds.version()` both return *no such function*), so no APOC-based bounded expansion is claimed.

Practical consequence for this project: keep `max_hops` small, filter by relationship type where the question allows it, and never treat a result cap as protection against a supernode — it protects the response size, not the database.

### A defect this benchmark caught

The first filtered run returned the same row count as unfiltered. The pattern had been built as `[LINKS*0..2]`, which Cypher reads as *a variable named LINKS* matching any relationship type, not a type filter. The colon (`[:LINKS*0..2]`) is required. The measurement disagreed with the intent, which is how it was found.
