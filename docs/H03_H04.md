## H03 — parity, and the defect it found

`evals/live_neo4j_parity.py` seeds a purpose-built graph (a diamond, a cycle, an
aliased entity and an isolated node) into a real Neo4j and compares every traversal
against `KnowledgeGraph.traverse`.

### The defect

The shipped `cypher_expand` built its query as a `UNION` of seeds-at-hop-0 and
`MATCH p = (s)-[*1..N]-(m)`. That returns **one row per path length**, so:

```
FAIL  no duplicate nodes (live)     11 rows for 9 distinct nodes
FAIL  min hops per node (diamond)   mem d=1   live d=2
FAIL  cycle safe (live)             10 rows for 8 distinct nodes
FAIL  ordered result parity
```

The in-memory engine keeps each node once at its **minimum** hops; the live query did
not. Downstream that means duplicate nodes and inflated counts in any result shaped
by `top_k`. Note this contradicts the comment in `tests/test_graph.py`, which claimed
the UNION form mirrored the in-memory engine — it did not.

### The fix

```cypher
MATCH (s:Node) WHERE s.id IN $seeds
WITH collect(s) AS seeds UNWIND seeds AS s
MATCH p = (s)-[*0..N]-(m:Node)
RETURN m.id AS node, min(length(p)) AS hops
ORDER BY hops, node
```

A zero-length pattern (`*0..`) includes the seeds, so no `UNION` is needed, and
`min(length(p))` gives one row per node at its minimum distance.

### A second discovery while fixing it: query shape matters

`MATCH (s) WHERE s.id IN $seeds MATCH p = (s)-[*0..N]-(m)` **followed by** the `WITH
... min()` aggregation still returned duplicates on this version — `c` and `seed` each
appeared twice when two seeds could both reach them. Introducing a
`WITH collect(s) AS seeds UNWIND seeds AS s` step before the expansion fixed it.
Reporting case: seeds `['aliased','e']` gave 9 rows instead of 7.

The reason is not established (it would need `PROFILE` of the plan shape), so it is
recorded as observed behaviour with the query that works, not as an explanation.

### Result

```
15/15 probes passed   (was 10/15)
```

Covering: seeds at hop 0, no duplicates, node-set parity at 1 and 2 hops, minimum
hops per node, cycle safety, undirected traversal, `score = 1/(1+hops)`, alias
extraction, parity from extracted seeds, isolated nodes excluded, and exact ordered
sequence parity.

### Incidental finding, not fixed

Seed extraction matches single-character entity ids in almost any query: an entity
with id `e` is extracted from "what is the Alias Target". The harness masks this only
because it uses a wide alias. A minimum-length or word-boundary rule would be the fix;
it is recorded rather than silently changed, since it alters retrieval behaviour.

## H04 — what actually bounds expansion work

`evals/high_degree_bench.py` builds `bench-leaf-1 -> bench-hub -> bench-leaf-2..N`
plus a `NOISE` branch from the hub, then measures four variants using the shipped
methods.

**`dbHits` is the metric that matters**, taken from `PROFILE`. Wall-clock varies with
machine, cache and row transfer; `dbHits` is the work the database actually performed.

| N | variant | rows | dbHits | median |
|---|---|---|---|---|
| 2000 | unbounded 2-hop | 2401 | **9210** | 48.5 ms |
| 2000 | capped `limit=10` | 10 | **9210** | 5.9 ms |
| 2000 | hop-bounded (`max_hops=1`) | 2 | **11** | 2.8 ms |
| 2000 | rel-filtered (`LINKS`) | 2001 | **8010** | 42.7 ms |

### Findings

1. **A result `LIMIT` does not bound traversal work.** At every size the capped
   variant returned 10 rows while `dbHits` was identical to unbounded — 9210 at
   N=2000. The database still expanded the whole neighbourhood. The lower wall-clock
   is row transfer and rendering, not less work. This is precisely why the conclusion
   rests on `dbHits`: on time alone it would have looked like a win.
2. **A hop bound does bound work.** `max_hops=1` needed 11 dbHits against 9210.
3. **A relationship filter reduces work in proportion to the subgraph it skips.**
   9210 → 8010 hits and 2401 → 2001 rows. Useful, not a general bound.
4. **`dbHits` grows linearly with degree** (≈4.6 per reachable node), so cost is
   proportional to the neighbourhood, not to `top_k`.
5. **No degree-aware expansion is available** without APOC or GDS, so no APOC-based
   bound is claimed.

### The defect the benchmark found — in the benchmark

The first filtered run returned the same row count as unfiltered. The pattern was
`[LINKS*0..2]`, which Cypher reads as *a variable named LINKS* matching **any**
relationship type. A colon is required: `[:LINKS*0..2]`. The measurement disagreeing
with the intent is how it was caught; `tests/test_neo4j_store.py` now pins the colon.

## What this establishes, and what it does not

**Establishes:** the Neo4j backend now reproduces the in-memory engine exactly across
15 probes including diamonds and cycles; a real defect in the shipped query is fixed
and the fix is verified against a live database; and there is a measured, deterministic
account of which bounds reduce expansion work and which do not.

**Does not establish:** production scale or performance. The graphs are synthetic and
small (≤2401 nodes); the timings are one machine on one day and are not portable;
`dbHits` is Neo4j-version-specific. No APOC/GDS behaviour was tested. The
query-shape behaviour above is observed on 2026.09.0 only.
